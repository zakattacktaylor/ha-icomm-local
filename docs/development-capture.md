# Green-hosted capture harness

Implementation: `addons/icomm_emulator`. This is the first development milestone,
not a finished cloud replacement. The add-on has been built on an ARM64 Green,
and its legacy TLS profile and management authentication were checked there.
Real heater traffic and UDP decoding remain separate acceptance gates.

## Behavior

- The management API listens on TCP 8787 and requires a per-installation bearer
  token on every route. It has no unauthenticated health/status endpoint.
- POST `/capture/start` starts one recording window of 10–300 seconds. TLS on
  8444 and UDP on 55055/55056 exist only during that window.
- TLS terminates locally and makes a separately verified connection to the real
  Ayla server. Raw HTTP streams are forwarded unchanged in both directions,
  preserving OEM Host, authorization, Date, encoding and framing.
- Each UDP client/port has its own connected upstream socket. Datagrams/replies
  are byte-preserving and associated with that client. The upstream server IP
  must be known; this recorder does not guess the destination of arbitrary
  router-DNATed packets or transparently handle endpoint rotation.
- Caller-supplied peer addresses are allowlisted. Storage is bounded to 24 MB
  per run; forwarding continues if the recording limit is reached.
- POST `/capture/stop` can require the current capture ID, protecting a later
  session from a stale stop request. Expiry also closes active connections.
- GET `/captures/<id>/archive` exports a stopped recording with authentication.
  Archives include raw traffic, not TLS private keys or the management token.
- The add-on initially uses manual startup and does not start at boot.

The server generates a private RSA/SHA256 certificate and standard ffdhe2048
parameters in its private data directory. The public Entrust Root CA G2 in the
source is a trust anchor for the development upstream connection only, not a
shared installation secret or a global trust-store change. SHA-256 fingerprint:
`43DF5774B03E7FEF5FE40D931A7BEDF1BB2E6B42738C4E6D3841103D3AA7F339`.
Remove the upstream dependency when implementing the fully local emulator.

## Gateway window

`tools/router-capture-window.sh` is a reviewed template, not an automatic router
installer. Supply explicit heater, gateway, Green and observed upstream IPs.
It restricts rules by source, destination, protocol and port, with a maximum
240-second independent gateway expiry and per-run tags. Partial installation
failure rolls back. Repeated cleanup of absent rules does not expire unrelated
newer sessions. It never flushes a firewall table.

UDP forwarding is **off by default**. The initial Green test redirects HTTPS
only and observes UDP passively at the router. Enable UDP forwarding only with
a current verified destination, because a router DNAT strips the original
server identity from what the recording socket can see. Capture a fresh device
registration when source-port/NAT changes would otherwise invalidate the old
notification session.

Arm the Green listener before the gateway window, and make the gateway window
shorter than the Green listener lifetime. A controller must attempt cleanup and
restore temporary gateway SSH settings even after an error. Verify rule removal
and listener expiry before changing any network policy permanently.

## Validation

Synthetic tests cover:

- Upstream TLS verification and exact HTTP request/response forwarding.
- Two separate UDP clients with exact request/reply preservation.
- Rejection of an unauthorized UDP source and API request.
- Invalid capture lifetime and stale-ID stop rejection.
- Storage-limit behavior and gateway cleanup on partial installation failure.

These tests establish transport behavior, not real-heater UDP compatibility.
A real transcript must still validate keys, framing and notification behavior.
No temperature/mode/configuration command is generated by the capture harness.

## Hardware result: November 11, 2026

A coordinated ordinary heater restart produced five verified upstream TLS
connections and a complete XML identity/bootstrap exchange on the Green.
The HTTP response supplied a fresh 64-byte base64-decoded ANS key; its first
16 bytes decode this device's notification traffic. Older saved keys failed.
The packet capture contains 64 records, including duplicate observations from
router `any` capture: registration plus encrypted registration responses,
keepalives, probes, request-probes and their replies. All 62 encrypted records
passed CRC validation. Registration signatures matched SHA1(message + the
16-byte key), rather than HMAC. The independent encoder reproduces all captured
encrypted records byte for byte when supplied their captured IV and padding.
These observations validate the format against this heater, but do not yet
prove a locally generated notification or a fully offline cloud replacement.
Raw captures, identities and keys remain private and are not included here.

A second bounded run forwarded HTTPS and both UDP ports through the Green.
A read-only app status request produced a decoded UDP notify, the heater's
acknowledgment, an HTTPS commands GET and a fresh telemetry POST. The service
forwarded 26 datagrams with no reported TLS failures. Both runs removed their
router rules and left the capture service inactive. This verifies the relay
path; no locally generated notification, WAN-blocked operation, or HA control
cutover has been proven yet.

## Experimental local service (0.3.0-dev1)

`emulator.py` adds a single-device HTTPS endpoint and UDP notification server,
with no upstream network client. Authenticated management routes are:

- `PUT /emulator/profile`: provision private captured identity XML, device ID,
  DSN, local ANS IPv4 address and optional existing registration ID. Never commit
  this profile. Provisioning is refused while either implementation is active.
- `POST /emulator/start` with `seconds` (10–300), `/emulator/stop`, and
  `GET /emulator/status`: bounded runtime, fresh telemetry and event summaries.
- `POST /emulator/notify`: an empty-command notification for transport testing.
- `POST /emulator/control` with `kind` (`target` or `mode`) and `value`: requires
  a local notification session and telemetry younger than 120 seconds. Commands
  are delivered once, expire after 30 seconds, and require post-delivery telemetry
  for confirmation. No captured cloud commands or schedules are replayed.

Capture and emulation are mutually exclusive. A generated local auth token is
used in responses; captured cloud authentication headers are not replayed.
`tools/router-emulator-window.sh` provides a separate maximum-240-second router
watchdog for source-scoped redirects and routed IPv4/IPv6 denial. Its LAN subnet
is currently specific to the development installation and must be reviewed
before using elsewhere. These rules are not a persistent production deployment.

The add-on includes generated copies of the pure protocol modules because its
Docker build context is its own directory. Run `python3 tools/prepare_addon.py`
after changing the integration codecs; a test checks these copies match.

Hardware status: local HTTPS telemetry has been received with routed Internet
access blocked. Initial local identity/bootstrap retries remain under diagnosis;
local UDP registration, generated notification delivery and control have not yet
passed the offline hardware test. The emulator client/config flow is implemented
in the integration source but has not been installed on the Green. The original
LAN-key path is retained. Do not treat this version as ready for routine use.
